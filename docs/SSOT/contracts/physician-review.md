# Physician review contract

Completed visits are patient-reported historical occurrences. Future, cancelled and rescheduled appointments are separate records and cannot reset the completed-visit anchor. Corrections append a revision with identity and recorded-at provenance. Invalid/future completed times fail validation.

Report periods use explicit start-inclusive/end-exclusive instants, a named timezone, a capture cutoff, and a versioned definition. Presets include 7, 28 and 90 calendar days and 6/12 calendar months; since-visit begins at the last completed occurrence, never a booking. Custom bounds must be ordered and cannot extend beyond capture. Missing visit history requires another explicit range.

Physician previews are immutable captured values. Full-period and monthly summaries retain per-metric eligible/available/unknown counts; recent 14/28-day detail complements the full period. Original units, source, instrument/content and derivation versions remain visible; incompatible versions are not pooled. Excluded or serious reports remain in the review detail appendix. Patient notes and questions are unscored; no ESS/KSS/NSS wording or inferred score is provided. Preview does not send data. Sharing requires an explicit action on the captured preview; later corrections create another snapshot.

SQLite `physician_review_records` retains completed-visit revisions and immutable previews. Failed reads block new preview creation; failed transactions publish no success. Reusing an identical revision/snapshot ID is idempotent; a conflicting payload or stale correction fails. Preview export uses protected temporary JSON and reversible formula-safe summary/detail CSV; temporary files are removed when the share sheet closes. The snapshot retains the source-coverage disclosure, app version, query period and timezone. Monthly represented-date denominators are clipped to the selected part of each month, independently from the full-period denominator.

The printable PDF is rendered from the same immutable report values and source details as preview/JSON/CSV. It paginates long questions and retained review detail without clipping. Unknown-time observations are retained as unplaced detail but cannot enlarge the selected-period eligible denominator.

Portable JSON explicitly names its numeric timestamp epoch (seconds since 2001-01-01T00:00:00Z) and preserves the stored precision. Recent detail uses the last included calendar day for a midnight-exclusive cutoff. Decoded periods and snapshots are revalidated before display or sharing.

Descriptive report contexts preserve shared diary coverage, sampling distributions and source provenance without entering numeric metric denominators. Raw event/questionnaire/intent evidence remains in JSON/CSV and source inspection; serious or ambiguous detail remains in the printable review appendix. Every calendar month intersecting the exact period appears in a separate coverage calendar, including months with no recorded observations. An empty month has zero dated source rows/dates, not a zero metric or an invented eligible episode. Report purpose and readable findings precede the final snapshot-ID/version provenance block.

Numeric summaries exclude partial measurements by default. When the user explicitly selects the dashboard's include-partial policy, the immutable report preserves that choice and counts finite, dated partial contributions separately from complete available observations. Missing-value or unknown-time partial rows never enter numeric summaries. The displayed source states and eligible/available/partial denominators do not change when that policy changes.

Human-readable comparison labels accompany exact source/version compatibility keys. Differing labels remain separate groups; unknown context is never silently pooled with a documented reference.

## Explicit report source preparation

The report adapter consumes `visibleInspectionNights`, preserving the selected sleep source, dose-pattern/work/context filters and exact stable identities. Missing filter evaluation or incomplete local dose/context/work reads fail preparation; a valid retained filter with no matching nights is an ordinary empty night selection. Independent daytime assessments and events retain their own actual occurrence-time membership and are not removed by night filters.

Report membership is the original inclusive-start/exclusive-end interval, independent of the dashboard's broader provider retrieval window and 18:00 treatment-date grouping. An interval's source start and required ending occurrence must be inside that interval before a numeric report contribution is accepted. Missing original provider boundaries or endpoints at/after the exclusive end withhold the numeric contribution with a partial-window explanation; raw values/source IDs remain visible. Recorded amounts are preserved as source evidence and never inferred from medication plans.

The shared dose-pattern, sleep-metric and replay projections remain the calculation authorities. Source and definition versions, compatibility strata, raw review revisions, and missing states survive into the immutable report. The selected provider supplies sleep metrics; the adapter does not add the other provider's primary sleep outcome as an extra result. WHOOP original endpoint contribution remains unavailable until the validated provider transport supplies it.

Legacy morning questionnaire fields can contain materialized defaults or carried-forward values. These records are always unconfirmed `needsReview` details with unknown assessment time. They cannot contribute to confirmed metric/category summaries, including when partial values are enabled. Their stored timestamps, original values, uncertainty and serious flags remain visible for review.

Daytime rating samples are separate from independently recorded events. Shared diary analysis supplies sampling groups and counts of full/partial reviewed intervals, event counts and calendar dates; no inferred sleep episode or clinical score is derived from a custom rating. Frozen work/medication compatibility grouping and historical reminder intent/open/response evidence will be added through their shared validated source adapters, not a new report-owned ledger.
