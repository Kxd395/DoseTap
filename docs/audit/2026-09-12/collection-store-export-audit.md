## Apple Health and WHOOP

DoseTap requests Apple Health **sleep analysis, heart rate, respiratory rate, HRV SDNN and resting heart rate**. Sleep sample categories include in-bed, awake, unspecified asleep, core, deep and REM. Timeline/summaries derive durations and boundaries from those observations. The app is not storing Apple's underlying sensor signals or a complete replica of the Health database.

The newer reviewed-night path retains sample/source evidence in memory: sample ID, original boundaries/category, source app name/bundle/version/product/OS, optional device description and supplied timezone, plus query time. It resolves coverage/conflicts and calculates read-only dose/sleep intervals. **That richer evidence is not persisted in SQLite or fully exported by Settings.** Legacy Settings enrichment queries 18:00–12:00 for the date and emits selected summaries, source names and reduced asleep/awake intervals. Consequently a later export can differ if provider data or permissions change. This is a known integration gap, not evidence that your Health data disappeared.

Apple documents [sourceRevision](https://developer.apple.com/documentation/healthkit/hkobject/sourcerevision) as the source app/device information. Apple's [HRV quantity is SDNN](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/heartratevariabilitysdnn); DoseTap still has a legacy timeline point member named `rmssd` holding that Apple value. Do not label or combine it as WHOOP RMSSD. The exported generic `hrvMs` also needs a method identifier for reliable cross-provider analysis.

WHOOP's optional path reads sleep/recovery through its [official API](https://developer.whoop.com/api/): sleep period and nap context, light/deep/REM/awake/in-bed totals, disturbance count, efficiency/performance/consistency, respiratory rate, sleep-need components, recovery, RMSSD HRV, resting heart rate, blood oxygen and skin temperature where supplied. These are provider summaries, not a timestamped awake episode that can by itself locate Dose 2 within an awakening. Availability/completeness and recovery-enrichment failure must remain visible. Live account access and owner records were not checked in this run.

## What the Settings controls actually do

1. **Export Studio Bundle** calls `StudioBundleExporter.writeStudioExportBundle`. It discovers local treatment dates, reads current consent, awaits provider enrichment, then builds events.csv, sessions.csv, inventory.csv, insights_bundle.json and collected_nights.csv for sharing. It is not a raw database dump.
2. **Scheduled Export** uses the same local bundle builder and publishes a ZIP after staging it, but does **not fetch provider enrichment**. It records the local-only warning. The existing cancellation/ZIP fixture passes. Scheduled and manual export parity applies to mapped local records, not provider content.
3. **Export Session Diagnostics** is a separate diagnostic flow. It is not a clinical archive or full database export.
4. The share sheet showing a bundle is not evidence a recipient/Files destination received it. The actual owner phone share/save/import round trip remains open.

There is no single manifest enumerating every expected row/field and proving source-to-export parity. The manual export snapshots the date list before awaiting provider calls, then rereads local rows; a concurrent new date/change can make enrichment and local data refer to different moments. The final synchronous local writer has no await between file projections, but there is no explicit database-wide export snapshot/error inventory. Add concurrent-edit and read-failure fixtures before claiming a coherent archive.

## Split-brain assessment

- **Repository baseline:** main equaled origin/main at 253cd3e; no open PRs at audit start. All three build-50 post-merge workflows passed: CI 34667493042, Swift CI 34667493036, Documentation CI 34667493009. Legacy `/Volumes/Developer/projects/DoseTap` was not used for implementation or copied into shipping code.
- **Primary database:** `EventStorage` opens Documents/dosetap_events.sqlite. `EventStore` in DoseCore is a protocol, not a second database. Its app implementation delegates to EventStorage. SessionRepository owns UI access and medication projections. The app/core morning bridge explicitly forwards scalar and raw payload fields; the duplicated type names are not themselves competing stores.
- **Medication/check-ins:** dose transaction, identity, correction, restart/failure and questionnaire atomicity suites pass. Source questionnaires, normalized submissions and derived symptoms are intentional projections with shared transaction boundaries; presence of several tables alone is not split-brain.
- **Confirmed remaining risk:** EventLogger has an optimistic in-memory event/cooldown before a Void storage write. The rejection probes show SQLite can contain no row without a failure result. That path needs repair before making a global “no split-brain” claim.
- **Reporting differences:** reviewed sleep evidence versus legacy export calculations, explicit Dose 2 diary versus inferred wakeSignal, current schedule context versus historical work facts, and reduced export metadata are semantic divergence risks. Preserve separate source meanings until their contracts are reconciled.
- **Unverified:** same-night phone views, device-restored data, permissions, external provider data, and staging sync. Automated tests do not close those gates.
